# 版本管理

仓库根目录保存当前版本源码，不再嵌套一份 `V0.2` 源码目录。原版与 V0.2 的独立开发历史通过合并保留，可以从提交记录和标签查看每次变化。

## 分支与标签

- `main`：最新可用源码。
- `legacy/v0.1`：保留原版源码，对应 `b69bffa`。
- `feature/功能名称`：开发新功能，检查通过后合并到 `main`。
- `fix/问题名称`：修复问题，检查通过后合并到 `main`。
- `v0.1.0`、`v0.2.0`、`v0.2.1`：固定发布点。已发布的标签不移动、不覆盖；有变化就发布新版本。

## 发布步骤

1. 完成代码及使用说明，检查提交内容中没有 API 密钥、个人数据或构建产物。
2. 同步更新 `package.json`、`package-lock.json` 中的版本号，并在 `CHANGELOG.md` 写明日期与变化。
3. 在源码目录运行：

   ```powershell
   npm ci
   npm test
   npm run build
   ```

4. 涉及阅读、窗口、API 或同步流程的改动，再运行 `npm run test:runtime`。需要便携版时，在 Windows 上运行 `npm run package`。
5. 检查通过后提交并合并到 `main`，为该提交创建新的附注标签，例如：

   ```powershell
   git tag -a v0.2.2 -m "Release v0.2.2"
   git push origin main
   git push origin v0.2.2
   ```

小修复使用补丁版本（如 `0.2.1` → `0.2.2`）；一组新功能可使用新的次版本（如 `0.3.0`）。版本说明应描述用户能感知的变化及必要的兼容性说明。

## 查看或运行旧版

在单独目录检出所需标签，避免覆盖当前源码。例如：

```powershell
git worktree add ../epub-reader-v0.1.0 v0.1.0
```

进入该目录后按对应版本的 README 安装和启动。切换源码不会自动回退应用数据；不要删除或重置个人数据来切换版本。V0.1 与 V0.2 使用各自的数据目录，同属 V0.2 的补丁版本通常共享数据，因此运行旧补丁前应先备份当前数据。
